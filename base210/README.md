# Base-210 (CRT residue) arithmetic: comparison and carry

Working notes + verification for the comparison / carry / divisibility TODOs in
the blog post
[*Base 210*](https://github.com/sh1boot/sh1boot.github.io/blob/master/_posts/2024-04-29-base-210.md),
which represents each base-210 digit as a Chinese-Remainder-Theorem triple
`(r₅, r₆, r₇) = (d mod 5, d mod 6, d mod 7)` (5·6·7 = 210) and notes
*"I'm not sure how to carry to the next digit. TODO: figure that out."*

Everything below is checked by the scripts in this directory; the figures are
generated by the `figures_*.py` scripts.

## 1. The digit is free; only the carry is hard

When you add two digits `a + b (+cᵢₙ)`, the **output residues** are just the
channel-wise sums `((a₅+b₅) mod 5, (a₆+b₆) mod 6, (a₇+b₇) mod 7)`. This is exact
*regardless of whether a carry happens*, because **210 ≡ 0 (mod 5), (mod 6),
(mod 7)** — subtracting 210 to bring the digit back in range changes no residue.

The carry is `carry_out = 1 iff a + b + cᵢₙ ≥ 210` (always 0 or 1, since
`209+209+1 = 419 < 420`). That threshold is a *magnitude* question, and the
residue triple deliberately hides magnitude. This is the classic **residue
number system (RNS) comparison / overflow problem**: RNS is non-positional, so
magnitude comparison is the one genuinely hard operation. The carry isn't a gap
in cleverness — it's the fundamental wall of RNS.

A useful sanity check that the difference alone can't settle it: `(x−y) mod 210`
maps both `x>y` (difference `v`) and `x<y` (difference `210−v`) onto the same
residues, so sign is *not* a function of the residue difference. You need
position, i.e. magnitude.

## 2. Mixed-radix is the orderable form

The escape is to convert the triple to **mixed-radix** digits (place values
1, 5, 30):

```
d₀ = r₅                              (ones,    0–4)
d₁ = (r₅ − r₆) mod 6                 (fives,   0–5)   — ×5 mod 6 is just negation
d₂ = (4·(r₇ − r₅) + d₁) mod 7        (thirties,0–6)   — the only real multiply
```

**Lexical comparison of `(d₂, d₁, d₀)`, most-significant first, equals magnitude
comparison** (verified on all 44 100 pairs). `order_proof.py` shows the point
numerically: sorting by the raw residue triple leaves 10 757 pairs out of order,
while sorting by `(d₂,d₁,d₀)` leaves **0** — it reproduces `0…209` exactly.

The figures make it visual (`x > y`, black = true):

- `figures/base210_order.png` — the same table under three orderings: magnitude
  (clean triangle), residue-lex (a scrambled *plaid* — no magnitude order), and
  mixed-radix-lex (the clean triangle again).
- `figures/base210_evolve.png` — the triangle assembling **most-significant
  digit first**: sort by `d₂` → coarse 7-step triangle (scramble confined to the
  30-wide diagonal blocks); add `d₁` → scramble shrinks to 5-blocks; add `d₀` →
  clean. The plaid is self-similar and mixed-radix peels it off scale by scale.
- `figures/base210_compute.png` — the same morph in **computation order**
  (`(r₇,r₆,d₀) → (r₇,d₁,d₀) → (d₂,d₁,d₀)`): replacing `r₆` with `d₁` barely
  changes the order (10 566 → 10 496 inversions) even though `d₁` must be
  computed first; the leap happens only when `r₇` becomes `d₂`. `d₁` is invisible
  as an ordering yet required as an input to `d₂`.
- `figures/panel_*.svg` — standalone, annotated versions of those panels
  (3 px cells; red lines = leading-digit block, blue = second-digit block).

## 3. A human-tractable procedure

The whole point is to stay inside the small-modulus world the system is built
from. `compare_native.py` confirms that with the `×4 mod 7` step done as a
7-entry lookup, **the largest number that ever appears in a comparison is 11** —
no multi-digit addition, no large-magnitude comparison.

Memory footprint: one cycle — **`×4 mod 7` = 0, 4, 1, 5, 2, 6, 3** — plus two
subtraction rules. `d₂` alone decides **86 %** of comparisons; you rarely look
past the top digit. (Reordering the radices so the multiply lands on mod 5 gives
a sparser 5-entry cycle `0,3,1,4,2`, at the cost of the top digit deciding ~80 %.
One small multiply is unavoidable: for any ordering of {5,6,7} the second step
forces `inv(2)`.)

## 4. One primitive to rule them all: overflow

Negation is free — `210 − y` is just **mirroring each dial**, `r → (m−r) mod m`.
And then (verified for all pairs in `overflow.py`):

```
x ≥ y   ⟺   overflow( x + (210 − y) )
```

because `x + (210−y) = (x−y) + 210`, which reaches 210 exactly when `x ≥ y`. So
**carry, comparison, and sign-of-subtraction are the same operation**: implement
*overflow* once and derive the rest, reusing the addition kernel you already need
for carrying. Honest caveat: overflow is not *computationally* cheaper than
comparison — it still asks "did the sum reach 210?", the same magnitude question
— and there is one boundary wrinkle: `mirror(0)` collapses to all-zeros
(indistinguishable from 210, a full wrap), so `y = 0` is special-cased
(everything ≥ 0).

The whole investigation lands on a tidy conclusion: the system needs **exactly
one hard primitive — the carry/overflow** — and everything else (add, subtract,
negate, compare) is free dial-arithmetic. *It was always the carry.*
